# Day P2 — The web, HTTP and APIs

## 1. What I tested
- JSONPlaceholder practice API: single manual calls to `GET /posts`, `GET /posts/1`, `GET /posts?userId=1`, `POST /posts`, `PUT /posts/1`, and `DELETE /posts/1` using Postman with `{{baseUrl}}` variable.
- Postman Echo API: cookie setting/echoing (`/cookies/set?course=perf` and `/cookies`) and manual header token passing (`/headers` with `Authorization: Bearer practice-token-123`).
- Browser DevTools: inspected request timing phases on `jsonplaceholder.typicode.com/posts/1` in Chrome DevTools Network tab.

## 2. Key numbers
- `GET /posts`: 200 OK — 442 ms
- `GET /posts/1`: 200 OK — 599 ms (Chrome DevTools TTFB: 96.93 ms, total duration: 362.40 ms)
- `GET /posts?userId=1`: 200 OK — 633 ms
- `POST /posts`: 201 Created — 452 ms
- `PUT /posts/1`: 200 OK — 1052 ms
- `DELETE /posts/1`: 200 OK — 973 ms

## 3. What I observed
- Cookies set with `Set-Cookie` were sent back automatically by the client on subsequent requests without adding any manual headers.
- Bearer tokens were only sent when explicitly added to the `Authorization` header.
- In Chrome DevTools Timing breakdown, connection setup and SSL took 255.94 ms, while TTFB was 96.93 ms.
- Forcing the assertion `pm.test("status is 200")` to expect 201 correctly triggered an `AssertionError`.

## 4. What I learned
- HTTP is stateless; session persistence relies on cookies, tokens, or server-side session stores.
- A 200 OK status code does not guarantee a business transaction passed—assertions must also check response bodies to avoid false passes.
- In the Network Timing tab, "Waiting for server response" (TTFB) represents the server's own processing time.
