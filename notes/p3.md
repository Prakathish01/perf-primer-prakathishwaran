# Day P3 — SQL, Python and the numbers of performance

## 1. What I tested
- SQL Queries on T-SQL temporary tables `#Customers` and `#Orders` covering filtering (`WHERE > 500`), aggregation (`GROUP BY`, `COUNT(*)`), multi-table `JOIN`, outer join (`LEFT JOIN ... WHERE NULL`), and `TOP 3`.
- Python CLI tools: `tools/hello_args.py` for argument-driven line counting and `tools/pandas_practice.py` for CSV grouping.
- Performance statistics simulation: `tools/p3_stats.py` calculating mean, median, p90, p95, p99, and max across 1,000 response times with 10 vs. 60 outliers.

## 2. Key numbers
- By-hand calculation (10 samples): Average = 347.5 ms, Median = 131.0 ms, p90 = 140.0 ms (outlier: 2400 ms).
- Python 1,000-sample simulation (10 outliers / 1%):
  - Average: 319.6 ms
  - Median: 302.6 ms
  - p90: 352.3 ms
  - p95: 367.7 ms
  - p99: 423.3 ms
  - Max: 2666.5 ms
- Python 60-outlier comparison (6%): Average jumped to 414.6 ms and p95 exploded to 1685.0 ms, while median (306.2 ms) and p90 (367.7 ms) remained stable.

## 3. What I observed
- In SQL, an `INNER JOIN` silently dropped Bengaluru because Divya had no orders; only a `LEFT JOIN ... WHERE o.OrderId IS NULL` exposed customers with zero orders.
- In performance statistics, the average was skewed by a single bad outlier (2400 ms), hiding that 90% of requests finished under 140 ms.
- When slow outliers increased from 1% to 6%, p90 did not move at all, but p95 spiked by over 1,350 ms because the 6% tail crossed the 95th percentile threshold.

## 4. What I learned
- Why performance engineering reports p95: averages hide tail latency and distort normal traffic; percentiles give an honest, predictable measure of user experience.
- How to write small analysis scripts using `argparse` and `pandas` for grouping and percentile analysis.
- How to verify basket and order counts in SQL to validate load test execution results.
